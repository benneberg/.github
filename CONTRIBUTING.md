# Contributing

Thank you for taking an interest in my projects.

The repositories under this account cover a mix of software engineering, experiments, developer tools, AI systems, edge computing, and ideas that are still being explored.

Not every project is intended to become a production product. Some exist primarily to answer a question:

> What happens if we try this?

That distinction is important when contributing.

---

## Before contributing

Please check the individual repository's README and documentation first.

Different projects may have different:

- goals
- maturity levels
- architectures
- development workflows
- contribution requirements

If a repository contains project-specific contribution guidelines, those take precedence over this document.

---

## What I value

### 1. Understanding before implementation

A good contribution is not necessarily the largest contribution.

Before making substantial changes, try to understand:

- what problem the project is solving
- why the current architecture exists
- what constraints the project has
- whether the proposed change actually improves the system

Architectural discussion is welcome, especially before implementing significant changes.

### 2. Small, focused changes

Prefer changes that are:

- focused
- understandable
- independently reviewable
- easy to test
- easy to revert

Avoid combining unrelated refactoring, feature work and formatting changes in the same pull request unless there is a good reason.

### 3. Experiments are welcome

Some projects are deliberately experimental.

In those repositories, a contribution does not necessarily need to move the project toward production readiness.

It may instead:

- test an idea
- demonstrate an alternative architecture
- explore a technical limitation
- challenge an existing assumption
- provide evidence for or against a hypothesis

Useful experiments are valuable even when the result is:

> This doesn't work.

Documenting why something failed can be as useful as implementing something that succeeded.

---

## AI-assisted development

AI-assisted development is welcome.

AI tools may be used for:

- exploration
- research
- implementation
- debugging
- documentation
- testing
- refactoring
- generating prototypes

However, contributors remain responsible for the code they submit.

Please review AI-generated code critically and make sure you understand what it does before submitting it.

Particular care should be taken with:

- security
- authentication and authorization
- data handling
- dependencies
- generated configuration
- infrastructure changes
- concurrency
- error handling

The goal is not to avoid AI-generated code.

The goal is to use AI without outsourcing engineering judgment.

---

## Issues

Issues are useful for more than reporting bugs.

Feel free to open an issue when you have:

- found a bug
- identified a usability problem
- discovered an architectural concern
- proposed a feature
- developed an interesting alternative approach
- found something worth experimenting with
- identified documentation that could be improved

For experimental projects, questions and ideas are particularly welcome.

---

## Pull requests

Before opening a pull request:

1. Make sure the change is relevant to the project.
2. Read the repository documentation.
3. Test the change where practical.
4. Explain what changed.
5. Explain why the change was made.
6. Mention important trade-offs or limitations.

For larger changes, it is often better to open an issue or start a discussion first.

A pull request should make it reasonably easy for someone else to understand:

**Problem → Approach → Result**

---

## Architecture and design discussions

I particularly welcome thoughtful discussion around architecture.

If you believe there is a better approach, please explain the reasoning.

Useful architectural feedback might include:

- alternative designs
- trade-offs
- failure modes
- scalability concerns
- operational implications
- security implications
- maintainability concerns
- simpler approaches
- unexpected consequences

You do not need to agree with the existing architecture to contribute.

In fact, challenging assumptions can be one of the most valuable forms of contribution.

---

## Code quality

There is no single universal definition of "clean code".

The appropriate level of abstraction, testing and complexity depends on the project.

In general, prefer:

- clarity over cleverness
- explicit behavior over hidden behavior
- simple architectures over unnecessary abstraction
- meaningful names
- predictable interfaces
- useful tests
- documented non-obvious decisions

Avoid introducing complexity merely because a more sophisticated solution is possible.

---

## Experimental repositories

Some repositories may contain:

- unfinished prototypes
- proof-of-concepts
- abandoned experiments
- alternative implementations
- speculative architectures
- intentionally unconventional code

This is intentional.

Please don't assume that every repository is promising production support or long-term maintenance.

Sometimes the purpose of a repository is simply to explore an idea in public.

---

## Respectful collaboration

Technical disagreement is completely fine.

Personal attacks are not.

Keep discussions focused on:

- ideas
- evidence
- implementation
- trade-offs
- outcomes

Assume good intentions and challenge ideas rather than people.

---

## A final principle

The most interesting contributions are not always the ones that add the most code.

Sometimes they are the ones that make us ask a better question.

If you have an unusual idea, an alternative architecture, or an experiment that might reveal something interesting, feel free to bring it forward.
